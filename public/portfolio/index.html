설계 · AI가 실수 없이 일하게

AI를 더 똑똑하게가 아니라, 실수하기 어렵게

미노피아는 휴대폰 하나로 여러 AI에게 개발을 맡기는 1인 사무실입니다. 사람은 요청하고 세 번 승인할 뿐이고, 나머지는 AI와 규칙이 합니다. 그래서 신경 쓴 것은 AI의 실력이 아니라 AI가 일하는 환경과 절차입니다. 프롬프트 → 컨텍스트 → 하네스 → 루프 → 그래프, 다섯 단계로 정리했습니다.

단계마다 막은 한계

단계그대로 두면 생기는 문제미노피아의 장치
1. 프롬프트
지시		한 AI에게 다 시키면 역할이 섞이고 판단이 흐려짐기획(Gemini) · 계획(Claude PM) · 개발(Codex·Claude) · 평가(3명) · 검사(미노)로 역할을 나누고, 지시서 형식을 고정
2. 컨텍스트
정보 제공		사람이 매번 자료를 찾아 붙여야 함기획서·고른 시안·고른 스킬·프로젝트 규칙·프로젝트 위키가 지시서에 자동으로 들어감
3. 하네스
규칙 강제		"하지 마"라고 써도 AI가 어길 수 있음승인 순서를 DB가 강제, 비밀값은 서버에만, 프로젝트 저장소 11곳에 위험 명령 차단 훅
4. 루프
자가 검증		사람이 결과를 일일이 확인해야 함규칙 검사 → 3중 평가(반대 심문 포함) → 화면 평가 → 자동 다시 개발(최대 2번)
5. 그래프
경로 설계		복잡한 일이 어디서 멈췄는지 모름단계·승인 문(門)·자동 연결을 정해 두고, 건너뛴 칸까지 대화창에 보여 줌
설계 1 · 프롬프트

AI마다 한 가지 일만

한 AI에게 "기획하고 만들고 검사해"라고 하면 스스로 만든 것을 스스로 통과시킵니다. 그래서 일을 나눴습니다. 같은 AI가 만들고 채점하지 않게, 만든 쪽과 평가하는 쪽을 항상 다르게 둡니다.

  • Gemini · 기획요청을 기획서로. 완료 기준을 "(필수) 400px에서 한 줄로 보임"처럼 확인 가능한 문장으로 씀
  • Claude PM · 계획기획서를 작업으로 나누고 누가 할지 정함
  • Codex · Claude · 개발고정된 지시서 형식(할 일·범위·완료 기준·결과 보내기)으로 받음
  • Gemini A·B + 동료 AI · 평가같은 채점표, 다른 관점(사용자 시나리오·회귀 / 반대 심문 / 유지보수 구조·실행 검증)
설계 2 · 컨텍스트

자료는 AI가 알아서 챙긴다

소유자는 한 줄로 요청합니다. 개발 AI에게 넘어가는 지시서에는 아래가 자동으로 붙습니다.

  • 승인된 기획서와 완료 기준기획 승인 카드 하나에서 확인
  • 고른 시안Gemini 둘이 그린 화면 시안 중 고른 것
  • 개발 스킬요청에 맞는 스킬을 미리 골라 둠(화면 확인·보안 점검 등)
  • 프로젝트 위키업무가 배포까지 끝날 때마다 AI가 "이 앱은·화면과 기능·지난 결정·주의할 점"을 고쳐 씀. 다음 개발과 대화 질문에 참고 자료로 들어감
원칙. 위키는 사용자 글에서 만들어지므로 AI의 시스템 지시에 섞지 않고 "참고 자료"로만 붙입니다.
설계 3 · 하네스

어기라고 해도 못 어기게

규칙을 글로 쓰는 것만으로는 부족합니다. 어기면 시스템이 막도록 세 겹으로 묶었습니다.

  • DB가 순서를 지킴기획 승인 없이 개발, 결과 승인 없이 배포가 안 됨. 승인·기획서·결과는 추가만 되는 기록이라 고치거나 지울 수 없음
  • 비밀값은 서버에만토큰·키는 서버 secrets에만 두고, 화면·로그·커밋·AI 지시문에 들어가면 검사에서 걸림
  • 위험 명령 차단 훅프로젝트 저장소 11곳에 설치. 실행 전에 막고 이유를 AI에게 알려 줌
[미노피아 훅] 막는 것
  rm -rf / ~ . *          강제 push · main/release 바로 push
  --no-verify             supabase db reset / push
  DROP TABLE · TRUNCATE   .env 출력·쓰기 · 토큰처럼 보이는 글 쓰기
→ 커밋 전(git pre-commit): .env · 비밀값 · 삭제 SQL이 든 커밋 거절
Codex는 Claude의 훅을 못 씀. 그래서 같은 검사를 git 훅으로 걸고, 결과를 받을 때 서버가 한 번 더 검사합니다(AI가 지시를 무시해도 서버 검사는 통과 못 함).
설계 4 · 루프

사람 대신 AI끼리 검수하고, 증거가 없으면 믿지 않는다

결과가 오면 사람이 보기 전에 다음 순서로 거릅니다.

  • ① 규칙 검사 (AI 없음)시험 실패 · 빈 변경 · 비밀값이면 바로 다시 개발
  • ② 3중 평가 (100점)완료 기준 40 · 기획서 25 · 유지 조건 15 · 범위 10 · 품질 10. Gemini A는 사용자 시나리오·회귀(쓰는 순서대로 따라가 보고 기존 기능이 깨졌나), Gemini B는 반대 심문(안 된 이유를 찾는 역할), 동료 AI는 유지보수 구조·실행 검증(저장소 전체를 보고 직접 돌려 봄)
  • ③ 화면 평가미노가 결과를 빌드해 휴대폰·PC로 찍고, 사진을 기획서와 비교
  • ④ 판정평균 80점·위반 없음이면 통과. 아니면 고칠 것만 적어 자동으로 다시 개발(최대 2번). 같은 지적이 반복되면 멈추고 사람에게

실제로 고친 사례: 근거 없는 만점

시험 업무에서 개발 AI(Codex)가 "브라우저가 없어 화면 확인을 못 했다"고 보고했는데, 채점 AI 둘은 "가로 넘침 없음 확인"으로 만점을 줬습니다. 직접 브라우저를 연 동료 AI만 그 항목을 "부분"으로 봤습니다.

그래서 채점에 규칙을 더했습니다.

  • 증거 없는 "충족"은 "부분"근거가 파일·줄·시험·화면처럼 확인 가능해야 충족. 완료 기준 점수는 항목별 판정으로 계산한 값을 넘지 못함
  • 실행 기록 없는 화면 주장은 "부분"시험 기록에 화면을 실제로 연 흔적이 없으면 화면 관련 항목은 충족이 될 수 없음
  • 95점 이상은 근거 2개 이상일 때만아니면 90점으로 맞춤. 채점표에 95·85·70·50점 기준 예시
  • 관점 나누기셋이 같은 쪽으로 쏠리지 않게, 볼 수 있는 자료에 맞춰 역할을 나눔. 바뀐 코드만 받는 Gemini 둘은 사용 흐름·회귀와 반대 심문, 저장소 전체를 여는 동료 AI는 구조와 실행. 근거 없는 트집은 버림

설계 · 정리

AI를 믿기보다 절차를 믿는다

다섯 단계는 따로가 아니라 한 줄로 이어집니다. 역할을 나누고(프롬프트), 자료를 자동으로 건네고(컨텍스트), 어길 수 없게 묶고(하네스), 증거로 검수하고(루프), 전체 경로에서 사람은 세 번만 결정합니다(그래프).

AI 활용의 본질은 AI를 더 똑똑하게 만드는 것이 아니라, 이미 똑똑한 AI가 실수 없이 일할 수 있는 절차를 설계하는 것.

도전가 · 직접 부딪힌 것

모르는 것은 배우면서, 안 되면 방향을 바꾸면서 만들었습니다

  1. 시작

    휴대폰 하나로 AI에게 일을 나눠 맡기는 사무실을 만들기로 했습니다. 코딩 지식은 없었습니다. 제가 하는 일은 요청과 승인으로만 정했습니다.

  2. 승인은 기록으로 남기기

    승인·기획서·결과는 고칠 수 없는 기록으로 쌓이고, DB가 순서를 지키게 했습니다. "배정했다"와 "실행됐다"를 나눠서, 확인한 것만 화면에 보여 줍니다.

  3. 토큰 아끼기

    늘 지킬 규칙은 각 저장소에 두고, 지시서에는 할 일만 쓰게 바꿨습니다. 지시서가 4,144자에서 909자로 줄었습니다. 판단할 수 있는 건 AI를 부르지 않고 규칙으로 처리합니다.

  4. 실패에서 방향 바꾸기

    무료 Gemini 키로 웹 검색이 되는지 모델 24개를 직접 시험했고, 모두 안 됐습니다. 그래서 검색은 Exa가 하고 정리는 Gemini가 하도록 나눴습니다. 써 보니 안 쓰이던 Grok과 "Gemini 쉬운 개발"은 뺐습니다.

  5. 일하는 방법도 쌓기

    AI가 꺼내 쓰는 작업 설명서(스킬) 16개를 모아 11개 프로젝트에 넣었습니다. 원본을 고치면 버튼 한 번으로 모든 프로젝트가 최신이 되고, 모든 프로젝트 PR에는 UI 코드 검사가 돌아 빠진 상태·접근성 문제를 알려 줍니다.

  6. 읽기 쉽게 다시 그리기

    대화창이 "미니엉"만 반복해 읽기 힘들어 디스코드처럼 바꿨습니다. 말한 AI의 얼굴·이름·시각을 붙이고, 업무 알림은 색 막대 카드로, 점수는 칸으로 나눴습니다.

  7. 기억 남기기

    배포할 때마다 버전 노트가 Obsidian 지식 그래프에 자동으로 쌓입니다. 버전마다 만든 AI와 쓴 스킬로 이어집니다.

  • 3중 평가: Gemini 두 개가 같은 항목을 다른 관점으로 채점하고, 개발한 AI의 짝(Codex↔Claude)이 동료로 채점합니다. 점수와 평균을 보고 사람이 정하고, 평균이나 과반이 기준 미만이면 자동으로 다시 개발합니다.
  • Gemini 시안: 기획서가 나오면 두 Gemini가 같은 기획서로 화면 시안(와이어프레임·흐름)을 하나씩 그리고 서로 평가합니다. 사람은 하나를 고르기만 하고(승인은 그대로 3번), 고른 시안은 개발 AI에게 넘어갑니다.
  • 0원 제약 아래 설계: 무료 키로 무엇이 되는지 직접 시험해 기록하고, 규칙으로 할 수 있는 판단은 AI를 부르지 않습니다.
  • 믿을 수 있는 자동화: 확인한 상태와 출처만 보여 줍니다. 승인과 결과는 고칠 수 없는 기록으로 남깁니다.
