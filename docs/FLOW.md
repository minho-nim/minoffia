# 현재 업무 흐름

1. 사용자 요청·자료 → 프로젝트 확인 → Gemini 기획서 초안. 앱 상태 질문은 규칙, 일반 질문은 Gemini가 답한다.
2. **기획 승인(A)** → Claude PM 분배·계획 자동 제출. 작은 일은 규칙으로 바로 배정, PM 불가 시 Gemini 대체. PM은 저장소를 읽기만 한다. 확인 질문에 답하면 재계획한다.
3. 견본 먼저면 근무 중인 Studio A·B가 견본을 만들고 사용자가 하나를 골라 **견본 승인(P)**. Codex 실행 승인은 그 뒤에만 가능. 직접 개발은 이 단계 생략.
4. **실행 승인(E, 자동)** → 계획이 오면 앱이 기획 승인에 포함해 실행 승인을 기록하고 담당 AI를 바로 시작한다(앱이 열려 있을 때, 소유자 결정 2026-11-10 '승인 3개'). 확인 질문이 남은 계획·견본 승인 전에는 자동으로 하지 않는다. 담당 AI 실행. 개발은 Codex가 주(Linear 위임), Codex가 휴가면 Claude 보조 개발(루틴), 둘 다면 쉬운 일만 Gemini(Actions). 앞 작업이 있으면 그 작업이 끝난 뒤 앱이 시작한다. 모든 AI 작업에 실행 승인 필요.
5. 결과(diff·시험·스크린샷·출처) 수신 → 규칙 검사·교차 채점 → 사용자 검토. Claude 결과는 Gemini, Gemini/Codex 결과는 Claude가 채점하며 Claude 불가 시 Gemini 대체. 자동 수정은 최대 2회 후 사용자에게 넘긴다. Codex도 1회용 제출표로 결과를 직접 보낸다(못 보내면 수동 등록).
6. **올리기 승인(B)** → PR·CI 확인. Claude·Codex 자동 결과는 Claude가 승인된 diff 그대로 PR을 연다. 같은 계획의 다른 작업이 진행 중이면 승인 불가. Claude/Gemini는 시험 뒤 작업 브랜치만 미리보기용 push 가능하나 B 전 PR·병합·배포는 금지한다.
7. **배포 승인(C)** → 서버가 CI 통과한 정확한 커밋을 확인해 squash 병합·release fast-forward. main의 추가 변경이 있으면 사용자 확인, CI 진행 중이면 대기한다. 이 저장소 자체 운영 배포는 별도 소유자 요청 때만 한다.

수정 요청은 기존 맥락으로 재계획하고 새 작업은 실행 승인을 다시 받는다. 승인·버전별 중복 실행은 DB 원자적 예약으로 막는다. 화면과 DB의 승인 조건은 같아야 한다.

대화 화면은 계정에 저장해 기기 간 이어 보며, 개발일지용 대화는 프로젝트·업무 메시지만 남긴다. 실제 운영 검증 범위는 [현재 상태](STATUS.md), 당시 결정 근거는 [보관 안내](archive/README.md) 참조.
